Enterprise mode: POST /api/orders currently creates an order in a database transaction and pushes directly to the queue inside CreateOrderAction, risking lost messages or phantom jobs on rollback/crash. Refactor order placement to implement the Transactional Outbox pattern end-to-end:
1. Create revertible database migrations for `{{%outbox_messages}}` and `{{%processed_messages}}`.
2. Move order creation into `PlaceOrderUseCase` wrapped in `ConnectionInterface::transaction()`, atomically persisting the order via `OrderRepositoryInterface` and appending the `'order.placed'` event via `OutboxWriterInterface` (`DbOutboxWriter` bound in `config/common/di/outbox.php`). Keep `CreateOrderAction` strictly thin (no repository, DB connection, or queue producer injection).
3. Implement `OutboxRelayService` guarded by `MutexFactoryInterface` (`$mutexFactory->create('outbox_relay')->acquire(...)` with stale lock reclaim, bounded batch `limit`, exponential backoff, and `'dead_letter'` transition) and expose it via `outbox:relay` console command calling `StateResetter::reset()` and registered in `config/console/params.php`.
4. Implement an idempotent queue handler (`HandlerInterface`) that deduplicates `(consumer_name, idempotency_key)` against `{{%processed_messages}}` and register the handler in `config/common/params.php`.
