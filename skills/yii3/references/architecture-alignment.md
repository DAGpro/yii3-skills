# Architecture alignment

Decides WHERE code and config go. Applies to plan, implement, improve, fix, review and verify.

## 1. Resolve the architecture source (in this order)
1. **Architecture artifact** generated by `/aif-architecture`. Base skills (`aif-implement`, `aif-plan`, ...) already load it —
   reuse that, do not re-resolve. Check `.ai-factory/ARCHITECTURE.md` (or path from `paths.architecture` in `.ai-factory/config.yaml`).
   If it exists → it is the **authority** for folder structure, layers, dependency rules and naming.
2. **Rules** (`paths.rules_file`, `rules.<area>`, `AGENTS.md`) — already loaded by the base skills; they refine, and win over this
   extension's defaults when they are explicit.
3. **No architecture artifact → the project's actual folder structure** is the authority:
   - inspect the real structure of `src/` and `config/`;
   - open 2–3 existing, similar features (an action, its input/DTO, its service/repository, its route and DI entries)
     and replicate their layout, naming, namespaces and wiring;
   - if the project is empty/new, use the defaults in `conventions.md`.
4. `conventions.md` layout is only a fallback for gaps the sources above do not cover.

State in one line which source you used, e.g. `Architecture: .ai-factory/ARCHITECTURE.md` or `Architecture: inferred from src/`.

## 2. Map Yii3 artifacts onto the architecture
Before creating a file, decide its place by asking the architecture (or the existing tree) for:
action/handler, input DTO/validation rules, domain/service classes, repositories/DB access, entities/ActiveRecord models,
events/listeners, console commands, migrations, views/layouts, tests, and the config files (routes, DI, params, bootstrap).
- Respect the **dependency rules** from the document (e.g. domain must not import infrastructure or `yiisoft/db`/HTTP classes;
  handlers depend on interfaces). A Yii3 package class is infrastructure unless the document says otherwise.
- Respect the **layout variant** (layers vs vertical slices vs flat): put new feature code where the variant puts it. See `feature-recipes.md` for layout examples and artifact graphs.
- Routes/DI/params go to the config files the project already uses for that purpose, under the same naming scheme.
- New packages must be used only from the layers allowed to depend on them.

## 3. Conflicts and drift
- Document vs. actual code disagree → follow the **document** for new code, do NOT refactor existing code, and report
  `WARN [architecture-drift]` with the specific mismatch.
- Document vs. Yii3 mechanics conflict (e.g. layer rule makes DI wiring impossible) → keep the document's intent,
  solve it with an interface + DI definition, and mention the decision in the task summary.
- Never create a new top-level folder or a second structure style silently. If the task truly needs one, stop and ask,
  or propose an `/aif-architecture` update.
- Do not edit the architecture artifact from these skills; suggest `/aif-architecture` if it must change.
